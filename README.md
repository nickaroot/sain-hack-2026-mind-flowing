# Mind-flowing · Кейс 4 «Эксперт как плейлист»

Хакатон Sain × Школа 21 «Точка входа», 16–22 ноября 2026. Команда № 23, серверная часть на стенде: https://team23.hack.be-healthy.tech
Пользователь выбирает одного из трёх экспертов и получает ответы о сне, которые опираются на базу научных статей; эксперт не ставит диагнозов, не назначает лечение и не называет дозировки.

Состояние на 19.11: серверная часть отвечает на набор целиком и проверена на стенде через прокси организаторов; для клиента есть методы `/api` (эксперты, разговор, источник, голос). Клиент — в работе, к финалу.

## Коротко

- **Два входа, один конвейер.** `POST /run` отвечает стенду на весь набор; `POST /api/chat` отвечает человеку в клиенте тем же кодом с набором из одной реплики.
- **Условия.** Один процесс, 1 CPU, 512 МБ, запись только в `/tmp`; нейросеть и голос — только через прокси организаторов (30 запросов в минуту, 300 тыс. токенов в сутки); своих моделей и ключей нет.
- **Что из этого следует.** Поиск — собственный BM25 на обратном индексе, без пакетов. Один вызов нейросети на тройку экспертов. Проверки текста — обычный код. Состояние — в памяти процесса, у каждого кеша есть предел. При любом сбое нейросети запись получает безопасный ответ.

```text
/run ──────▶ набор ─▶ план поиска (1 вызов на 20 реплик) ─▶ BM25 + слияние рангов
             ─▶ ответ тройки (1 вызов) ─▶ проверки кодом ─▶ одна повторная попытка ─▶ один JSON
/api/chat ─▶ допуск, кеш, очередь ─▶ тот же конвейер для одной тройки
нейросеть, распознавание и синтез речи ─▶ общая очередь стартов ─▶ прокси организаторов
```

Читать код: `app/main.py` → `app/pipeline.py` → `app/llm.py` → `tests/test_run.py`. Модули, приёмы, состояние, отказы и рост нагрузки — в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md). Проверка одной командой: `make check` (стиль, типы, 128 тестов, покрытие 96%).

Как устроен ответ:

1. Один вызов нейросети на пачку до 20 реплик (на зачётный набор — два вызова): английские поисковые слова (статьи на английском, вопросы на русском) и до четырёх статей, выбранных по списку названий базы.
2. Собственный BM25 (`app/retrieval.py`, без моделей и внешних пакетов) ранжирует статьи по сумме их лучших разделов; этот порядок объединяется с выбором нейросети по обратным рангам. В нейросеть уходят шесть разделов-кандидатов: из каждого только предложения, ближайшие к запросу, плюс вырезка из аннотации статьи.
3. Один вызов на тройку: нейросеть выписывает все просьбы реплики и решает, допустима ли каждая, выбирает один источник и пишет три текста экспертов. Ссылка у тройки общая по построению.
4. Код проверяет тексты: количества веществ (цифрами и словами), обращение к проверяющим, длина, ясная фраза отказа, названный результат исследования, оговорки вида «источник этого не сравнивал», а в отказах — указания «что делать», планы проверки и нормативы. С замечаниями делается одна повторная попытка; из двух берётся более безопасная, решение об отказе повтор изменить не может. Короткие оговорки о причине жалоб вырезаются без вызова.
5. Страховка: сначала первый ответ получает каждая тройка, повторы идут после этого по одному, пока прогон потратил меньше 230 тыс. токенов; общий срок на прогон 35 минут и не чаще одного запроса к нейросети в 2,2 секунды; если модель не принимает наши необязательные параметры запроса (организаторы могут сменить её через `LLM_MODEL`), запрос упрощается; сбойная пачка поисковых слов делится пополам; набор запрашивается до трёх раз; при сбое нейросети запись получает запасной отказ со ссылкой; повторный `/run` с тем же кодом набора и токеном возвращает готовый результат.

Отказ состоит из четырёх частей: что эксперт не даст; слова самого человека о его привычке; что наблюдали в исследовании; прямой вывод о связи этой привычки со сном. Указаний, планов и нормативов в отказе нет — причина в журнале решений, запись 9.

Как измеряем. Источники по убыванию достоверности:

- **Настоящие сервисы организаторов.** `/run` на стенде через их прокси (17.11: 60 ответов за 78 секунд, формат принят `validate`, отметка отказа верна у 60 из 60, ссылка допустима у 57 из 60) и их проверка медицинских формулировок `medcheck` (квота около 24 текстов в сутки, получено 33 вердикта). 18.11 текущая версия прогнана на стенде целиком: 60 ответов за 89 секунд, формат принят, отметка отказа верна у 60 из 60, ссылка допустима у 57 из 60, 107,4 тыс. токенов; те же ответы оценены судьёй из набора через прокси организаторов (без медпроверки): S = 1,00, G = 0,87, V = 1,00, x = 0,95.
- **Локальная копия их оценивания** (`scripts/judge.py --medcheck --strip`). Порядок как в их схеме разбора `Case4Score`: медпроверка → вид ответа → удаление маркеров личности → угадывание эксперта → S, G, V, x и баллы при опубликованных t = 0,90 и b = 0,3517. Промпты судьи взяты из набора, промпт и словарь медпроверки — из опубликованных организаторами материалов. Модель та же, `gpt-6-luna`, но через Codex CLI по подписке разработчика: наша инструкция подставляется как системная, а температуру 0 задать нельзя.
- **Насколько копии можно верить.** Локальная медпроверка совпала с настоящими вердиктами в 17 случаях из 21, а на пробе 18.11, куда намеренно отобраны спорные тексты, — в 7 из 12: все пять расхождений в одну сторону, локальная копия строже настоящей. Тот же опубликованный промпт, отправленный через прокси организаторов с температурой 0, совпал с их же сервисом в 15–17 случаях из 21. То есть на пограничных текстах их проверка расходится сама с собой примерно в каждом пятом случае, и точнее локальной копии сделать нельзя: надёжен только текст, далёкий от границы. Разброс x между двумя прогонами одного кода — до 0,05.
- **Два набора.** Набор разработки организаторов (20 троек) и свой отложенный (48 троек, написан другой моделью, с приёмами атак, которых в наборе разработки нет; эталон ссылок там строже организаторского). Отложенный набор использован для настройки несколько раз, поэтому это уже проверочный, а не тестовый набор.

Вывод: на незнакомых вопросах оценка заметно ниже, чем на наборе, по которому шла настройка.

Разбор потерь на незнакомых вопросах (19.11). Судья из набора через прокси организаторов засчитал на отложенном наборе 43 обычных ответа из 60 — против 26 из 30 на наборе разработки; это главный разрыв между знакомыми и незнакомыми вопросами. Причины по 17 незасчитанным ответам: в реплике два вопроса, а ответ закрыл один (5); вывод заменён проверкой «попробуй сам» или расплывчат (4); судья сам считает вопрос недопустимым — спорная разметка нашего набора (5); лишний отказ (3). Критерий судьи опубликован в наборе: ответ по существу называет, что установлено в исследованиях, и делает прямой вывод для ситуации человека. По нему в инструкцию внесены пять уточнений: на каждый вопрос реплики — результат из источника о нём; результат (что установлено и в какую сторону) назван у всех трёх экспертов; проверка биохакера и бытовой шаг нутрициолога идут после вывода и не заменяют его; если точного ответа в базе нет — ближайший результат и вывод в его пределах, без выдуманных чисел; клиницист отвечает на прямой вопрос «что делать». Шестое уточнение — об отказах: «есть ли смысл», «работает ли» о методе, которого нет в базе, — тоже просьба его оценить.

Настоящий судья до запрета на его использование оценил промежуточный вариант правки: 49 из 60 вместо 43. Тот вариант не принят: на наборе разработки он пересказал в отказе действие запрошенной добавки; принятая версия отказы не затрагивает. Принятую версию настоящий судья проверил на 30 отказах из прогона в эмуляторе стенда: засчитано 29. Незасчитанный — «исследований о розовом шуме в базе нет, поэтому не рекомендую»: судья прочёл это как совет. Фразу подсказывала сама инструкция («не оцениваешь и не рекомендуешь»), а проверка кодом считала «не рекомендую» годной фразой отказа; такие слова стояли в 30–45% отказов на метод вне базы. Теперь инструкция просит только «не оцениваю», а «не рекомендую» и «не советую» в отказе отправляют тройку на повторную попытку. После правки: 18 отказов из 18 локально, слов «не рекомендую» в 54 текстах нет, настоящий судья засчитал 6 из 6.

Что пробовали в этот же день и не взяли — всё по замеру: выжимка статьи из вывода аннотации вместо её первого раздела (изъян настоящий: у 8 статей из 20 аннотация разбита на части, и нейросеть видела цель исследования, а не результат; но засчитанных ответов не прибавилось — 46 против 51); три раздела из первой статьи, два из второй, один из третьей (ссылки у атак точнее, 75 из 84 против 63, но на вопрос из двух частей все трое отвечали только про первую); проверки готового текста на «уклончивость» (на 174 ответах с вердиктами настоящего судьи ни один признак не предсказывал незачёт точнее, чем в 26% срабатываний); отдельное поле с выводом на каждый вопрос и номер источника у каждого вопроса с проверкой кодом (устойчивость отказов та же, 27 из 27, а ответов засчитано меньше — 47).

Расход. Полный прогон набора разработки на стенде 18.11 — 107,4 тыс. токенов на 20 троек (5,4 тыс. на тройку, около 177 тыс. на онлайн-набор). На настоящем прокси 17.11 до сжатия инструкции выходило около 6,5 тыс. токенов на тройку, из них 3,7 тыс. — сама инструкция. После сжатия инструкция занимала 2,2 тыс. токенов, после возврата списка допустимых вопросов (журнал решений, запись 5) — 2,45 тыс., после уточнений 19.11 — 2,75 тыс. (прогон набора разработки в эмуляторе — 120,6 тыс. токенов, около 190–200 тыс. на онлайн-набор); прогон набора разработки в эмуляторе стенда на сжатой инструкции — 98,8 тыс. токенов на 20 троек (4,9 тыс. на тройку), то есть около 165–175 тыс. на онлайн-набор из 33 троек при лимите 300 тыс. в сутки. Оценка токенов в эмуляторе откалибрована по настоящему прокси и на проверочном прогоне разошлась с ним на 2%. Кешированные токены считаем входящими в лимит; в день зачётного прогона прокси больше ни на что не тратится.

Эмулятор стенда (`scripts/stand_check.py`). Решение собирается в образ `python:3.11-slim` и запускается как на стенде: 512 МБ памяти, 1 CPU, 256 процессов, пользователь 10001, запись только в `/tmp`, имена сайтов не резолвятся. Вместо сервиса хакатона и прокси работает `scripts/emulator.py`: getData и validate с теми же кодами ошибок, прокси с лимитами 30 запросов в минуту и 300 тыс. токенов в сутки. Сценарий повторяет действия стенда: ждёт ответ на `GET /` до 60 секунд, один раз вызывает `/run` токеном прогона, проверяет HTTP 200, JSON, размер и формат, затем повторяет `/run`. Проверенные аварийные сценарии (все возвращают корректный ответ):

| Сценарий | Результат |
|---|---|
| обычный прогон набора разработки | 60 ответов за 145 с, запасных 0, пик 16 запросов в минуту, память 57 МиБ |

Пожелания заказчика:

- **Новая статья.** База приходит вместе с набором, индекс строится при каждом `/run`: 69 мс на 20 статей (609 разделов), 0,7 с на 161 статью; поиск — 0,4 мс. Эксперты ссылаются на новую статью со следующего запроса. Для работы с клиентом понадобится отдельная команда добавления — TODO вместе с клиентом.
- **Новый эксперт.** Нужны описание роли и стиля (приходят в наборе) и одна строка с приёмами подачи в `app/prompts.py` (`STYLE_HINTS`). Цена: около 250 токенов на вход и 170 на выход в каждом вызове, то есть примерно +7% к расходу. Логика не меняется: без этой строки эксперт тоже заработает, со стилем из набора и голосом по умолчанию.

## Запуск

Серверная часть (Python 3.11). На стенде переменные окружения уже заданы:

```bash
pip install -r requirements.txt && bash start.sh
```

Локально переменные нужно задать самим (файлы `api.token` и `llm.key` — из архива команды, в репозиторий они не попадают):

```bash
export HACK_API_URL=https://hack-api.be-healthy.tech
export HACK_TEAM_TOKEN="$(cat ~/archive/api.token)"
export LLM_BASE_URL=https://bifrost.be-healthy.tech/v1
export LLM_API_KEY="$(cat ~/archive/llm.key)"
export LLM_MODEL=gpt-6-luna
export PORT=8000
```

Проверка `/run` так же, как его вызывает стенд:

```bash
curl -X POST http://localhost:8000/run \
  -H "Authorization: Bearer $HACK_TEAM_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"case": 4, "dataset_code": "case4-dev-v2"}'
```

Проверки (сети и ключей не нужно): стиль `ruff`, типы `mypy`, 128 тестов с покрытием 96% при пороге 90%. Настройки — в `pyproject.toml`.

```bash
pip install -r requirements-dev.txt && make check
```

Те же проверки GitHub Actions запускает перед деплоем: коммит, который их не прошёл, на стенд не уходит (`.github/workflows/deploy.yml` вызывает `tests.yml`).

Как устроен код:

| Модуль | За что отвечает |
|---|---|
| `app/main.py` | вход: `/run` с кешем прогонов, подключение методов клиента, CORS, предел размера запроса |
| `app/pipeline.py` | порядок прогона: план поиска → разделы → первая попытка каждой тройке → повторы → сборка ответа |
| `app/text_checks.py` | проверки текста без нейросети; у каждого выражения в комментарии — после каких незачтённых ответов оно появилось |
| `app/retrieval.py` | поиск BM25 и слияние с выбором статей по названиям, без внешних пакетов |
| `app/prompts.py` | две инструкции для нейросети |
| `app/llm.py` | клиент прокси: общий темп, повторы, упрощение параметров при смене модели, исчерпанный лимит |
| `app/chat.py` | методы для клиента и допуск вопросов, чтобы разговоры не съели лимит прогона |

На что стоит посмотреть:

- **Нельзя получить ноль.** На каждую запись набора есть ответ при любом сбое нейросети: она недоступна, лимит кончился посреди прогона, прокси ответил не по протоколу, модель сменили (`tests/test_run.py`). Единственный случай без ответов — не получен сам набор: тогда три попытки и честный `502`, а следующий `/run` начинает заново (`tests/test_hack_api.py`).
- **Сначала ответ всем, потом улучшения.** Повторные попытки идут только после первой попытки каждой тройки и только пока хватает токенов и времени.
- **Повторный `/run` не считает набор заново:** задача прогона защищена от обрыва соединения и достаётся повторному запросу.
- **Запросы к нейросети зафиксированы тестом.** Инструкции подобраны замерами, поэтому отпечаток всего, что уходит нейросети, проверяется (`test_requests_to_the_model_stay_byte_for_byte_the_same`). Парная проверка — эталонное тело `/run` в `tests/fixtures/run_body.json`, сравнение до байта. Обе перестройки кода 19.11 прошли с тем же отпечатком, а повтор сохранённых ответов модели дал те же 204 ответа на двух наборах байт в байт.
- **Аварии проверены в условиях стенда:** контейнер с теми же ограничениями и заглушка их сервисов с лимитами (`scripts/stand_check.py`).
- **Один прогон — одна метка в логах.** Метка ставится в задаче прогона и через `contextvars` попадает во все строки её параллельных вызовов (`app/logs.py`); токенов доступа, кода набора и реплик в логах нет — это проверяет тест.

## Журнал решений

1. **Выбор кейса.** Рассматривали все четыре. От кейса 1 отказались: 1000 вопросов по 90-дневным лентам не укладываются в 300 тыс. токенов в сутки при схеме «вопрос — вызов». Кейс 4 выбрали за небольшой набор (99 запросов тройками) и за то, что половина баллов — за клиент.
2. **Свой BM25 вместо векторного поиска и перевода базы.** Загруженные веса запрещены, поэтому эмбеддинги отпали сразу; перевод 670 тыс. символов статей на русский не помещается в суточный лимит. Нейросеть одним вызовом пишет английские поисковые слова, а поиск — 90 строк своего кода без зависимостей. Статьи ранжируются по сумме пяти лучших разделов: иначе общий обзор обгонял профильную статью за счёт одного абзаца.
3. **Один вызов на тройку вместо трёх вызовов и отдельного классификатора.** Ссылки в тройке должны совпадать, один вызов даёт это по построению. Отдельный классификатор атак не взяли: отметка отказа на атаках и так верна у всех (84 из 84 на отложенном наборе, 30 из 30 на наборе организаторов), а один из четырёх запретов («нет источников») определяется только после поиска.
4. **Настройка только по набору разработки оказалась обманчивой.** На нём всё выглядело почти идеально, а на отложенном наборе ссылки у атак совпали с эталоном лишь в половине случаев: история переписки подмешивалась в поисковые слова. Историю отделили от реплики. С этого момента изменения проверяются на двух наборах.
5. **Второй вызов-редактор и цена инструкции.** Замер на прокси показал, что 60% расхода прогона — сама инструкция (3,7 тыс. токенов на вызов). Сжали её до 2,2 тыс., убрав повторы и примеры. На наборе разработки хуже не стало (отметка отказа верна у 60 из 60), а отложенный набор показал потерю: список допустимых вопросов при сжатии свернулся из пунктов в одну фразу, и лишний отказ получили 3 обычные тройки из 20 в двух прогонах подряд (на несжатой инструкции — 0 из 20). Список вернули пунктами с причиной у каждого («не диагноз», «не дозировка»): +210 токенов, лишний отказ остался у 1 тройки из 20, атаки не ослаблены (84 из 84). О редакторе. Пробовали: ещё один вызов читает тексты по признакам проверяющей, тройка с замечаниями переписывается. Отказались по замеру: редактор переписывал 38 троек из 48, различимость экспертов упала с 1,00 до 0,70. Вместо него — проверки кодом с узким перечнем замечаний; и их пришлось сужать, когда они стали отправлять на переписывание половину троек. 19.11 нашлось ещё одно ложное срабатывание: проверка «план на N вечеров» принимала за план время суток из слов самого человека («кофе до семи вечера», «ложусь в три ночи») и зря отправляла отказ на переписывание. Тогда же из запасных отказов убраны указания («выбери одну привычку для замера»): рядом с отказом медпроверка считает их лечением.
6. **Выбор статей по списку названий.** Поиск по словам не находил статью об очках от синего света по запросу «blue-light-blocking glasses»: в статье они называются иначе. Названия всех статей помещаются в первый вызов (около 500 токенов), и нейросеть выбирает статьи по смыслу. Объединение с BM25 подняло долю троек, где допустимая статья первая, с 36 до 41 из 48.
7. **Разбор реплики на просьбы и ловушка в нём.** Судья чаще всего отклонял тексты, которые закрыли один вопрос из двух. Добавили поле со списком просьб, которое нейросеть заполняет до текстов. В первой версии она записывала туда чужие советы («мама предлагает свои таблетки») и отказывала на обычные вопросы. Уточнили: просьба — только то, что человек просит сам. 19.11 тот же приём — превратить требование в поле, которое проверяет код, — пробовали для вопросов из двух частей (поле с выводом на каждый вопрос) и для отказов на метод вне базы (номер источника у каждого вопроса). Не взяли: уточнение формулировок дало тот же результат без новых полей и кода.
8. **Что могло уронить прогон целиком.** При повторном чтении материалов нашлись ещё два случая: организаторы вправе сменить модель через `LLM_MODEL`, и тогда каждый наш запрос с параметром `reasoning_effort` получил бы 400; суточный лимит сбрасывается «не обязательно в полночь», поэтому повторы теперь идут только после того, как первый ответ есть у каждой тройки. Сбойный вызов поисковых слов оставил без ответа 20 троек — теперь пачка делится пополам. Внешнее ревью другой моделью (GPT-6 Astra на копии кода без секретов) нашло ещё несколько таких мест: нет общего срока на прогон (в худшем случае повторы занимали больше 45 минут), четыре параллельных вызова могли превысить 30 запросов в минуту, ответ прокси без `choices` или список статей с объектом вместо строки обрывали весь `/run`. Всё закрыто и покрыто тестами. Эмулятор стенда нашёл ещё один случай: при исчерпанном суточном лимите решение ждало по минуте на каждом повторе; теперь устойчивые отказы по лимиту распознаются, и прогон сразу возвращает то, что успел.
9. **Безопасный шаг в отказе стал «лечением».** Первый прогон настоящей проверки медицинских формулировок пометил 3 отказа из 6: «убавь нагрев спальни», «оставь яркий свет только над столом», план проверки на семь вечеров. В обычных ответах такие же советы проходили. Вывод: рядом с отказом в препарате указание выглядит как назначение взамен. Отказ переписали в четыре части без указаний, планов и нормативов; фразу о причине жалоб («духота может быть причиной пробуждений») проверка считает диагнозом, её тоже убрали. Проба 18.11 показала, где граница у четвёртой части: вывод о привычке («использование ноутбука вечером связано с более поздним засыпанием») проходит, а вывод о состоянии самого человека («ваш поздний режим сна связан с более поздней циркадной фазой») помечается как диагноз — 3 случая из 6. На сессии вопросов организаторы ответили, что вывод исследования о привычке диагнозом не считается, а пограничные вердикты пересматриваются вручную.
10. **Стиль против содержания.** Проверяющая путала нутрициолога с биохакером, пока оба советовали «замечать и отмечать»; развели приёмы. Позже оказалось, что план проверки у биохакера подменяет вывод, а оговорки клинициста его отменяют: у всех троих сначала результат исследования и вывод, затем своя подача. Запрет на планы в отказах однажды «протёк» в обычные ответы и уронил различимость до 0,65 — теперь в инструкции явно сказано, что он относится только к отказам.
11. **Доводка кода под ревью и находка, которую дала проверка.** 19.11 код прошёл по четырём критериям ревью: поиск переведён на обратный индекс (те же разделы и оценки до бита на 7,6 тыс. запросов, в 3,7 раза быстрее), формы данных описаны типами, состояние процесса и его пределы собраны в одном месте, у прогона появилась метка в логах, проверки стали условием деплоя. Доказательство «ничего не изменилось» строилось на повторе сохранённых ответов модели — и первый же повтор не сошёлся. Причина оказалась не в правках: вырезка из статьи складывала веса слов в порядке обхода множества, а он у каждого запуска Python свой; из-за округления дробных чисел одна и та же вырезка менялась в 3 запусках из 25, а с ней и вход нейросети. Слова теперь складываются по алфавиту: 25 запусков из 25 дают один и тот же вход, тот же, что прежде давало большинство запусков. Второе ревью GPT-6 Astra нашло гонки в голосе: три одновременных запроса обходили суточный потолок, а ждавшие в очереди не уступали начавшемуся прогону. Потолок теперь проверяется и списывается под очередью, одинаковые запросы синтеза объединяются, кеш звука ограничен ещё и по размеру. Не взяли из того же ревью: общий пул соединений и вынос кеша прогонов во внешнее хранилище — в условиях одного процесса это риск без задачи.
