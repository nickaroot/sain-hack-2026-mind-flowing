# Архитектура серверной части

Одна страница о том, как устроен код, почему так и что будет, если нагрузка или данные вырастут. Замеры качества и история решений — в корневом [README](../README.md), договор с клиентом — в [client/README.md](../client/README.md).

## Условия, под которые всё спроектировано

| Условие стенда | Что из него следует в коде |
|---|---|
| один процесс, 1 CPU, 512 МБ, запись только в `/tmp` | состояние в памяти процесса, без базы и очередей; у каждого кеша есть предел |
| нейросеть и голос только через прокси организаторов: 30 запросов в минуту, 300 тыс. токенов в сутки | одна общая очередь стартов для всех обращений к прокси; учёт токенов; сначала ответ всем, потом улучшения |
| загруженные модели и свои ключи запрещены | поиск — собственный BM25 без пакетов, проверки текста — обычный код |
| стенд вызывает `POST /run` один раз, без набора и без ответа — ноль баллов | повторы получения набора, запасной ответ на каждую запись, повторный `/run` не считает заново |

## Два входа, один конвейер

```text
стенд ──POST /run──▶ main.run ─▶ hack_api.fetch_dataset ─┐
                                                          ▼
браузер ─POST /api/chat─▶ chat (допуск, кеш, очередь) ─▶ pipeline.answer_dataset
                                                          │  1. план поиска: один вызов на 20 реплик
                                                          │  2. retrieval.Index: BM25 + слияние рангов
                                                          │  3. один вызов на тройку экспертов
                                                          │  4. text_checks: проверки кодом
                                                          │  5. одна повторная попытка, пока есть токены и время
                                                          ▼
браузер ─POST /api/transcribe, /api/speak─▶ voice ──▶ llm.wait_turn ──▶ прокси организаторов
```

Разговор в клиенте — это тот же `answer_dataset` с набором из одной тройки. Поэтому живой ответ проходит те же шаги и те же проверки, что и ответы, которые оценивает стенд, а одна правка конвейера действует сразу на оба входа.

Читать код удобно в таком порядке: `app/main.py` → `app/pipeline.py` → `app/llm.py` → `tests/test_run.py`.

## Модули и их границы

| Модуль | Отвечает за | Не знает о |
|---|---|---|
| `main.py` | HTTP-вход, `/run`, кеш прогонов, предел тела запроса, CORS, раздача готовой сборки клиента по `/app/` | поиске и текстах |
| `pipeline.py` | порядок шагов прогона и выбор лучшей попытки | HTTP и FastAPI |
| `retrieval.py` | обратный индекс, BM25, слияние рангов, вырезки | нейросети |
| `prompts.py` | две инструкции для нейросети | том, как их отправляют |
| `text_checks.py` | проверки текста регулярными выражениями | том, откуда текст |
| `llm.py` | прокси: темп, повторы, параметры модели, исчерпанный лимит | наборе и экспертах |
| `chat.py`, `voice.py` | методы клиента: допуск, очереди, кеши, суточные потолки | устройстве конвейера |
| `smalltalk.py` | разговорные реплики в чате: распознавание по набору целых фраз и готовые тексты | нейросети и наборе |
| `hack_api.py` | получение набора с повторами | всём остальном |
| `cache.py` | ограниченный кеш (LRU, пределы по числу и байтам, счётчики) и память пригодных ответов нейросети | том, что в нём лежит |
| `contracts.py` | формы данных на границах (`TypedDict`) | — |
| `state.py`, `logs.py`, `config.py` | общее состояние процесса, метка прогона в логах, настройки из окружения | — |

Зависимости идут в одну сторону: вход → конвейер → поиск, проверки, прокси. `pipeline` не импортирует FastAPI, `retrieval` и `text_checks` не импортируют ничего, кроме стандартной библиотеки и `contracts`.

## Приёмы и где они в коде

| Приём | Где | Зачем |
|---|---|---|
| Порт и адаптеры | `llm.JsonModel` (протокол); `llm.LLM` — прокси, `scripts/offline_llm.py` — повтор сохранённых ответов, `tests/fakes.FakeLLM` | конвейер получает модель параметром: тесты и локальная оценка идут без сети и без правок кода |
| Конвейер с этапами | `pipeline.answer_dataset`: `_prepare` → `_attempt` → `_better` → `_answers` | каждый этап — функция с ясным входом и выходом; предметные структуры `SearchPlan`, `Draft`, `Triple` |
| Управляемая деградация | `pipeline._fallback`, `llm.LLM.exhausted`, `RETRY_TOKEN_BUDGET`, срок прогона | при любом сбое нейросети запись получает безопасный ответ, а не пропуск |
| Идемпотентный запрос | `main.run`: задача по ключу «код набора + отпечаток токена», `asyncio.shield` | обрыв связи и повторный `/run` не тратят суточный лимит второй раз |
| Объединение одинаковых запросов | `chat._question_in_work`, `voice.speak`: словарь `in_work` | двойное нажатие и повтор после тайм-аута ждут уже начатую работу |
| Допуск с резервом | `chat._admit`, `voice.VoiceState.take_*` | открытые всем методы не могут выбрать лимит, нужный прогону |
| Общий ограничитель темпа | `llm.wait_turn` | один лимит запросов в минуту на нейросеть и голос |
| Один примитив кеша | `cache.BoundedCache`: ответы разговоров, звук, распознанные записи, ответы нейросети | у каждого кеша предел, вытеснение и счётчики попаданий; память не растёт от числа запросов |
| Кеш с допуском | `cache.ResponseCache`, запись в `pipeline._attempt` и `_search_plans` | запоминается только ответ без замечаний; сбой кеша отключает кеш, а не ответ |
| Обратный индекс | `retrieval.Index._postings` | запрос просматривает только разделы со своими словами |
| Метка запроса в логах | `logs.start_run` через `contextvars` | все строки одного прогона, включая параллельные вызовы, находятся по одной метке |
| Формы данных на границах | `contracts.Dataset`, `RunResult` | проверка типов без копирования и пересборки данных |

## Состояние

Всё состояние живёт в памяти одного процесса и одного цикла событий. Проверка и изменение счётчика стоят рядом, без `await` между ними — в этих условиях это и есть атомарность.

| Что | Где | Предел | Когда пропадает |
|---|---|---|---|
| прогоны набора | `app.state.runs` | по одному на код набора и токен | сбой или больше 10% запасных ответов — забывается сразу; иначе до перезапуска |
| последний набор | `app.state.dataset` | один | заменяется следующим `/run` |
| учёт токенов за сутки | `chat.ChatState` | три числа | в 00:00 по Москве |
| ответы разговоров | `chat.ChatState.cache` | 200, давно не читанные вытесняются | перезапуск |
| ответы нейросети для прогонов | `app.state.responses` | 600 записей и 8 МБ | перезапуск |
| ответы нейросети для разговоров | `chat.ChatState.responses` | 200 записей и 2 МБ | перезапуск |
| распознанные записи | `voice.VoiceState.heard` | 50 | перезапуск |
| индекс базы статей | `chat.ChatState` | один на набор | смена набора |
| озвученные ответы | `voice.VoiceState.speech` | 30 записей и 16 МБ | перезапуск |
| темп обращений к прокси | `llm._next_start` | одно число | — |

Границы гарантий, о которых стоит знать:

- Учёт токенов — оценка по ответам прокси, а не его ведомость: перезапуск и другие потребители ключа в неё не попадают. Поэтому у суточного лимита оставлен запас в 30 тыс. токенов.
- `RETRY_TOKEN_BUDGET` ограничивает улучшения, а не весь прогон: первая попытка делается для каждой тройки всегда.
- Запрос голоса, уже ушедший к прокси, не отзывается, когда начинается прогон. Таких не больше двух, каждый занимает у прогона один старт в очереди (2,2 с).
- Кеш прогонов не ограничен числом записей: стенд вызывает `/run` считаные разы, а вытеснение готового результата стоило бы полного суточного лимита.

## Кеширование

Кешируется всё, что стоит денег или времени, но на том уровне, где известно, что результат пригоден.

| Уровень | Ключ | Что не запоминается |
|---|---|---|
| результат `/run` (`main.run`) | код набора + отпечаток токена | прогон со сбоем или с долей запасных ответов больше 10% |
| ответ нейросети на шаг конвейера (`cache.ResponseCache`) | модель + инструкция + данные + параметры вызова | ответ не по форме, небезопасный, с любым замечанием проверок; неполный план поиска |
| ответ разговора (`chat.ChatState.cache`) | набор + пользователь + вопрос + история | ответ с запасным текстом |
| звук ответа (`voice`) | голос + текст | сбой прокси |
| текст записи (`voice`) | тип + байты записи | сбой прокси |
| индекс базы статей | сам список статей набора | — |
| начало инструкции у прокси | статичный текст идёт первым | — |

Почему кеш ответов нейросети стоит в конвейере, а не в клиенте прокси: клиент видит только «пришёл JSON», а пригоден ли он, знает конвейер. Если запоминать любой JSON, повторная попытка на тот же запрос получала бы из кеша тот же негодный ответ.

Что он даёт. В одном прогоне все запросы разные, и на первом вызове `/run` кеш ничего не меняет: на двух настоящих наборах ответы с ним и без него совпали до байта при том же числе вызовов. Он работает, когда прогон закончился с запасными ответами и `/run` вызвали снова: при сбое прокси на середине набора повтор стоил 13 вызовов вместо 24 (набор организаторов) и 38 вместо 61 (отложенный набор) и дал полный ответ. Без кеша второй полный прогон в суточный лимит не помещается.

Чего в ключах нет и почему это безопасно: пользователя и набора. Ключ — весь вход нейросети; два одинаковых входа дают один ответ, чей бы он ни был, а чужие данные во вход не попадают. Срока жизни у записей нет: сменился набор, инструкция или модель — сменился ключ. Разговоры и прогоны держат ответы нейросети в разных кешах: открытый всем метод не может ни подготовить ответ для стенда, ни вытеснить его.

## Отказы и что видит вызывающая сторона

| Что сломалось | Что делает решение |
|---|---|
| сервис хакатона не отдал набор | три попытки (сбой сети и 5xx), затем `502`; сбой не запоминается, следующий `/run` начнёт заново |
| прокси ответил 429 или 5xx | повторы с паузами в пределах срока прогона; устойчивый 429 считается исчерпанным лимитом |
| суточный лимит кончился посреди прогона | оставшиеся записи сразу получают запасной отказ, тело ответа остаётся полным |
| модель сменили и она не принимает параметр | набор параметров упрощается и запоминается |
| ответ модели не JSON или не по форме | тройка считается неотвеченной и идёт на повтор |
| текст небезопасен (количество вещества, обращение к проверяющим) | повторная попытка; если не помогло — запасной отказ |
| вызывающая сторона оборвала `/run` | прогон продолжается и достаётся повторному запросу |
| идёт прогон | методы клиента отвечают `503` с `Retry-After`, уже начатые вопросы прерываются |

## Как это растёт

**Больше статей.** Индекс строится за один проход: 50 мс на 609 разделов, 0,7 с на 161 статью. Поиск по обратному индексу — 56 мкс на запрос (перебор всех разделов давал 205 мкс) и зависит от числа совпавших разделов, а не от размера базы. Правильность проверена дважды: 7,6 тыс. запросов на двух настоящих наборах дали те же разделы и те же оценки до последнего бита, а `tests/test_retrieval.py` сверяет индекс с перебором на каждом запуске тестов. Предел подхода — список названий статей в первом вызове: после 300 статей (`CATALOG_MAX_ARTICLES`) он отключается, и выбор статей остаётся за BM25.

**Больше запросов в наборе.** Вызовы идут с общим темпом 2,2 с, поэтому время прогона — примерно 2,2 с на тройку: 33 тройки зачётного набора — около двух минут. Узкое место здесь не код, а лимит прокси.

**Больше пользователей.** Одновременно считаются два вопроса, ещё два ждут, остальным — `429` с `Retry-After`. Это осознанный предел: каждый вопрос стоит около 5,6 тыс. токенов из общего суточного лимита.

**Несколько экземпляров.** Сейчас это не нужно и на стенде невозможно, но путь понятен, потому что всё состояние собрано в нескольких местах:

1. Общий ограничитель темпа по ключу команды (сейчас `llm._next_start`) — во внешнее хранилище: он должен охватывать нейросеть, голос и повторы всех экземпляров.
2. Резерв и учёт токенов (`ChatState`) — одна атомарная операция в общем хранилище.
3. Прогон — запись с ключом идемпотентности, статусом и результатом вместо `asyncio.Task`; экземпляр-владелец с ограниченным сроком владения.
4. Версия набора — общая; индекс остаётся в памяти каждого экземпляра, он неизменяем и строится за доли секунды.
5. Кеши ответов и звука можно оставить локальными: это экономия, а не условие правильности. Память ответов нейросети (`ResponseCache`) при общем хранилище даст восстановление прогона после перезапуска — интерфейс `get`/`put` для этого менять не придётся.

Чего здесь намеренно нет: базы данных, брокера сообщений, нескольких процессов, агентных фреймворков. У каждого из них была бы цена в памяти и в сложности развёртывания, а задачи, которую он решал бы в этих условиях, нет.

## Как проверяется

| Что | Чем |
|---|---|
| поведение и отказы | 142 теста без сети и ключей (`pytest`), покрытие 96%, порог 90% |
| запросы к нейросети не изменились | отпечаток всех запросов и их параметров (`test_requests_to_the_model_stay_byte_for_byte_the_same`) |
| ответ стенду не изменился | эталонное тело `/run` в `tests/fixtures/run_body.json`, сравнение до байта |
| стиль и типы | `ruff`, `mypy`; настройки в `pyproject.toml` |
| условия стенда | `scripts/stand_check.py`: контейнер 512 МБ / 1 CPU / только `/tmp` и заглушка сервисов организаторов с их лимитами |
| качество ответов | `scripts/eval.py`, `scripts/judge.py` на двух наборах — см. README |

Всё вместе — `make check`. Перед деплоем на стенд те же проверки запускает GitHub Actions: коммит, который их не прошёл, на стенд не уходит (`.github/workflows/deploy.yml`).

## Как добавить

- **Эксперта** — он приходит в наборе вместе с ролью и стилем речи и заработает без правок. Строка в `prompts.STYLE_HINTS` добавляет приёмы подачи, голос — строка в `voice.VOICES`.
- **Проверку текста** — выражение и сообщение в `text_checks.text_problems`; сообщение уходит нейросети при повторной попытке, поэтому меняет отпечаток запросов.
- **Другую модель или поставщика** — класс с методом `chat_json` (протокол `llm.JsonModel`), передаётся в `answer_dataset`.
- **Правку инструкции** — только вместе с замером на двух наборах: отпечаток в тесте обновляется осознанно.
